04 / ENGINEERING DECISIONS

DESIGN EXAMPLE

A retry must not become a second submission.

A hypothetical design exercise, separate from the real project contribution above. No employer architecture or measured outcomes are represented.

TECHNICAL CHALLENGE

A file upload can succeed while metadata registration or an external extraction request fails. Retrying the whole workflow risks duplicate records and inconsistent review status.

DESIGN CHOICE

Make the decision explicit.

Separate file storage from workflow state. Use an idempotency key for one logical submission, with explicit received, processing, and review states.

Tradeoff This adds state management, but avoids treating a partially completed workflow as a single success or failure.

EXCEPTIONS & RECOVERY

Keep failure recoverable.

Validate file type and size before processing. Preserve accepted input on downstream failure; retry safe steps and send exhausted or uncertain cases for human review.

HOW I WOULD VERIFY THE DESIGN

Replay the same request, simulate an API timeout after upload, and restart a worker. Expect one logical record, a visible pending state, and a recoverable next step.
